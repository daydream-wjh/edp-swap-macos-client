## 新进展

从此前提取的 x86 驱动中定位到 AES S-box、逆 S-box，进一步定位到密钥展开及加解密函数。本轮没有只靠字符串或表特征下结论，而是在 Unicorn 的隔离内存中执行了相关纯计算函数，并以独立密码库和合成输入进行交叉验证。

该模拟器没有 Windows 内核、系统调用桥、设备句柄或主机磁盘映射。它没有加载真实内核驱动或启动客户端，也没有使用任何个人口令。不过，本轮已从纯静态分析推进到纯运算指令模拟，不能继续表述为“完全没有执行过目标指令”。

## 已验证

1. 首选 VA `0x12598`：AES-128 密钥展开。
2. `0x1266c` / `0x12726`：分组加密 / 解密，与独立 AES 实现结果一致。
3. `0x128dc` / `0x1281a`：包含额外派生和偏移处理的加密 / 解密包装。
4. 已编写不依赖 Windows API 的 Python 原型，复现这一个包装分支。以 64 字节合成数据、8 字节合成密钥，在字节偏移 0、16、512、4294967808 下，原型输出均与原驱动纯函数模拟一致，并通过往返恢复检查。
5. 底层便携 AES 实现另以 10 组随机密钥和随机分组，与独立密码库交叉检查，通过。

其中额外处理为：输入密钥循环扩展后与程序常量组合，展开为 AES 轮密钥，再按每个分组的 64 位字节偏移调整轮密钥。这里的偏移究竟相对于真实盘、交换区还是其他映射，尚未通过实际数据确认，不能直接用于真实盘解密。

## 对实际设备仍未知的部分

- 实际设备走哪一种驱动算法分支；驱动中存在多种分支，不能把本轮验证的算法视为通用实现。
- 分区描述、真实数据位置、正常口令验证和密钥派生方式。
- Mac 端真实磁盘读取、正确解密后文件系统识别以及安全写回。

算法原型不包含登录、设备指令、口令猜测或绕过认证逻辑。它不是解锁工具，不应对真实设备盲目使用。

## 实际设备状态

本轮 `diskutil list external` 未列出该物理 U 盘，`/Volumes/启动区` 不存在。只读首扇区脚本因挂载路径不存在而在设备识别阶段退出，没有读取其他磁盘。

随后 U 盘重新出现，系统再次列出 62.9 GB 物理设备，且启动区 EXE 的完整 SHA256 与输入副本一致。重新运行受限脚本仍在只读打开设备时返回 Operation not permitted。

进一步查询 TCC 日志，发现 root Python 对 SystemPolicyRemovableVolumes 的授权请求出现 XPC Connection invalid。这使“只需给 Codex 完全磁盘访问权限”的早先判断不充分。现已在可见 Terminal 窗口启动同一限定脚本，由本机交互式 sudo 完成权限认证；未读取或使用聊天中的密码。是否成功以生成的读取结果为准，不能仅凭终端打开或管理员授权成功认定。
