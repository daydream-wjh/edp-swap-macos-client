# 驱动与挂载依赖：进一步验证

## 已确认

1. 控制模块中的两个 Native PE 已通过版本资源确认为 EdpEDisk.sys，版本均为 `3, 6, 10, 28`，架构分别为 i386 和 AMD64。文件偏移分别为 `0x29cd8c`、`0x2aa68c`。这不是仅依靠驱动名称字符串的推断。
2. 偏移 `0x261a24` 的内嵌用户态 PE 为 EdpEDisk.dll，版本 `8198, 2100, 1120, 136`。导出包括 EdpStartService、EdpMountFile、EdpUnMountFile 等，并导入 Windows 服务管理和 DeviceIoControl API。
3. 控制模块的 `0x10029e80` 例程根据对象状态在 EdpEDisk.dll 和 EdpEDiskEx.dll 之间选择加载，然后解析 EdpStartService、EdpMountFile 等函数。由此可知存在不同实现分支，不能把一个模块的行为无条件推广到全部设备模式。
4. 含 UserLogin 日志交叉引用的登录例程在 `0x10026970` 调用上述加载例程；在 `0x100275d1` 通过全局函数指针 `0x10095120` 调用 EdpMountFile。这个指针在 `0x10029fcd` 的 GetProcAddress 调用后赋值，因此调用关系得到代码证据支持。
5. 已提取的 EdpEDisk.dll 中，EdpMountFile 位于首选 VA `0x100098c0`，调用 `0x10007350` 的内部例程。内部例程在 `0x10007450` 调用 DeviceIoControl，并传入 `0x8200e018`。这表明该挂载实现不是只用普通文件 API；该控制操作的具体驱动与语义仍需继续核实。

这些都是静态代码证据，尚无动态执行验证。并未修改登录判定或绕过任何检查。

## 本机与设备的实时核验

- macOS 27.2（26B118），ARM64。
- 外接物理盘当前为 disk4，总容量 62.9 GB，分区表工具仅列出 10.5 MB 启动区，其余显示空闲；这一结果不能证明其他扇区不含数据。
- 当前可用磁盘空间约 27 GiB。
- 当前用户对 `/dev/rdisk4` 的只读打开被拒绝。随后尝试通过 `sudo -n` 运行限定的单扇区读取脚本，结果为 `sudo: a password is required`，未读取扇区、未写入设备。

## 尚未解决

- 两个加载分支在这支实际 U 盘上哪一个生效。
- 驱动是否参与该设备模式下的全部交换区访问。
- 认证与数据访问的完整协议、加密格式、Mac 端设备传输和文件系统接入。
- 真实口令登录及文件读取验证。

因此目前不能交付或宣称存在可用的 Mac 解锁程序。常规分析会沿现有证据推进；真实设备验证必须先满足系统授权及明确命令语义，不能由离线分析成功代替。

## 证据

`静态分析证据/embedded-details.json` 记录各内嵌 PE 的版本、架构、导入导出；`login-xrefs.json` 记录登录日志引用；`userlogin.asm`、`mount-loader.asm`、`mount-exports.asm`、`mount-core.asm` 和 `service-core.asm` 保存静态汇编摘录。

地址是各模块自己的首选 VA，同一数值在不同 DLL 中可指向不同内容。摘录并非高级语言反编译或完整控制流恢复，边界和分支仍需逐项验证。
